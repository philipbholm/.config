# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

Personal dotfiles/config directory for a macOS development environment. Version-controlled configs for shell, editor, terminal, window manager, coding agents (Claude Code, Codex CLI, Cursor agent CLI), and development workflow scripts targeting a Docker-based monorepo (Ledidi medical platform).

## Repository Structure

- `zsh/.zshrc` — Zsh config (symlinked to `~/.zshrc`). Key custom functions: `notify` (run command with macOS notification on finish), `tdl`/`tdlm`/`tsl` (tmux IDE layouts), `eff` (fuzzy open file). Aliases: `n` (nvim), `g` (git), `d` (docker), `t` (tmux attach/create), `ff` (fuzzy find with preview). Tool inits for eza, zoxide, fzf, starship, mise.
- `claude/` — Claude Code config: settings (model, permissions, plugins, hook declarations), custom agents, custom skills, `statusline-command.sh`, and `bin/` helpers. Both agents and skills are split by profile, and **every skill of our own is now work-only**: `claude/skills.work/` holds all nine (review-pr, learn, distribute, explain-diff-html, fix-pr-feedback, and the four vendored-and-recalibrated superpowers skills — brainstorming, writing-plans, test-driven-development, systematic-debugging), while `claude/skills/`, `claude/agents/` and `claude/agents.work/` are empty `.gitkeep`-only dirs kept so the installer's link calls stay uniform. A personal machine therefore gets none of our own skills — its `~/.claude/skills` is empty, and the only skills it has come from plugins (described below). Hook *scripts* live in `dev/` (see `dev/claude-notify.sh`).
  - **Matt Pocock's skills come straight from the plugin.** `settings.json` enables `mattpocock-skills@claude-plugins-official`, so its 22 declared skills are reachable under the plugin namespace — `mattpocock-skills:tdd`, `mattpocock-skills:wayfinder`, and so on. Nothing in the installer touches them: `/plugin update` is the whole update path and needs no reinstall afterwards. (An earlier local setup symlinked each of them into `~/.claude/skills` to drop the prefix, with the plugin disabled so nothing was listed twice; since the cache path carries the plugin version, every link dangled after an update. `cleanup_stale` in `install-common.sh` removes any left behind.) Editing one of these skills edits the plugin cache, which is not version-controlled and is overwritten on update; vendor a copy into `claude/skills.work/` under a different name if you want a change to survive.
  - The four vendored superpowers skills came from that plugin's cache. superpowers is no longer listed in `enabledPlugins` at all, though its cache is still on disk as the reference copy. The vendored copies were rewritten for Opus 5 per [Anthropic's prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5): narrower `description` triggers, no rationalization/red-flag tables, no verification checklists or self-review gates, no mandated subagent handoffs. Re-apply those rules when editing them.
- `codex/` — Codex CLI config: `config.toml` (model, trusted projects, MCP servers, enabled plugins) and `rules/default.rules` symlinked into `~/.codex/`. Skills are **copied, not linked**: `install-common.sh` rsyncs every dir under `codex/skills/` (currently `code-review` and `explain-diff-html`) into `~/.codex/skills/`, because Codex's loader doesn't follow symlinked skill dirs — so editing one here has no effect until the installer is re-run.
- `dev/` — Development helper scripts symlinked to `~/bin/`. Core scripts:
  - `dev.sh` — Dev stack manager (auto-detects main vs worktree, wraps docker compose with correct override files). `dev nuke` needs `--yes` whenever stdin is not a tty — which is every agent Bash call — and is in `permissions.ask`.
  - No verification wrapper lives here anymore: the monorepo's own `lefthook.yml` gates all six workspaces (services/registries, services/patient-bff, apps/registries-frontend, apps/patient-frontend, apps/shell, packages/components), so run the underlying commands directly — `npm run build-ts`, `npx vitest run`, `npx biome check` — from the workspace you changed.
  - `tunnel.sh` — Cloudflared tunnels for frontend + API
  - `setup-stack.sh` — Prepare a worktree for work: npm install for the three workspaces the stack needs, type generation, supergraph composition, then a `sync-context` run so the worktree has its context files. It starts no containers; Docker and ports come from `dev up`. `--all` (or named workspaces) also installs the rest of the workspaces lefthook gates — several GB per worktree, hence opt-in; it warns at the end about any gated workspace left without `node_modules`.
  - `lib/workspace.sh` — Sourced by the other scripts. Owns stack identity (slot files under `~/work/.dev-stacks`, workspace/slot Docker labels), the base ports, and `dev_apply_context_ports`, the single placeholder substitution both `dev.sh` and `sync-context.sh` call.
  - `wt-down.sh` — Tear down the worktree you are standing in: `dev nuke --yes` (running it is the confirmation), then — only once its containers are verifiably gone — remove the directory and re-sync context. Refuses on a dirty tree and never deletes the branch (unlike the retired `gwd`, which discarded uncommitted work). There is no creation counterpart — worktrees are created natively by Claude Code's `EnterWorktree`. Run only **after the PR is merged**; agents never invoke it (nor `dev down`/`dev nuke`) on their own initiative.
  - `mcp-datadog.sh` — Datadog MCP launcher shared by all three agents; maps `DD_API_KEY`/`DD_APP_KEY` → `DATADOG_*` so no secret lands in a tracked config
  - `claude-notify.sh` — macOS notification hook for Claude Code (Stop + Notification events) plus an on/off switch. Wired via the `hooks` block in `claude/settings.json`. Toggle with `claude-notify on|off|toggle|status`; state in machine-local `~/.claude/notify.state` (missing = enabled). Suppresses false "idle/done" alerts while Claude is busy: drops events from subagent transcripts, the redundant `idle_prompt` notification, and Stop while `background_tasks` (subagents/teammates/shells) are still in flight — so "done" only fires when genuinely at rest. Posts via `terminal-notifier` (osascript floor); clicking the banner focuses Alacritty. `codex-notify.sh` is the Codex equivalent, wired via `notify` in `config.toml`. (Both used to post to Telegram — that was retired 2026-08 in favour of macOS notifications.)
- `dev/context/ledidi-monorepo/` — Agent context templates for the monorepo. `dev/sync-context.sh` copies `CLAUDE.local.md` and `AGENTS.md` into the main repo and every worktree, substituting the `{{*_PORT}}` placeholders from that worktree's slot (or replacing the whole port section when no stack is running). The two files are kept byte-identical apart from the H1, and `sync-context` aborts rather than spread a divergence; the main checkout gets its own port and teardown wording, since it owns slot 0 and `wt-down` refuses to run there. `docs/` is **not** copied — the templates link those by absolute path, so their port placeholders stay literal and must be substituted from the port table by whoever reads them.
- `dev/feedback/` — PR review learnings extracted by the `/learn` skill (mine/ and other/), distilled into `SYNTHESIZED_LEARNINGS.md`, which `review-pr` loads
- `dev/.env.local.example` — Key names for the ngrok/NHN values `dev.sh` sources from the gitignored `dev/.env.local`
- `aerospace/aerospace.toml` — AeroSpace tiling WM (alt-based keybinds, vim-style navigation)
- `alacritty/` — Terminal config (JetBrainsMono Nerd Font, light/dark themes via symlink, Left Option as Alt for tmux)
- `tmux/tmux.conf` — Omarchy-style config; prefix Ctrl-Space (+ Ctrl-B secondary). `prefix+z` kills the pane and `prefix+Z` kills the window, neither confirming, and there is no zoom binding — worth knowing before you send either. The bindings are documented once, in [GUIDE.md](/Users/philip/.config/GUIDE.md) § Tmux; read it there rather than restating them here. `tmux.conf` itself is the ground truth if the two ever disagree.
- `git/config` — SSH commit signing, separate work identity via includeIf for `~/work/`. Git verifies against the **generated** `~/.ssh/allowed_signers`: `git/allowed_signers` is the tracked base, and `install-work.sh` appends the work key from `~/.ssh/github_work.pub`, so no per-machine key is committed. Re-run the installer after restoring keys.
- `gh/config.yml` — GitHub CLI settings (`co` alias for `pr checkout`). `gh/hosts.yml` is machine-local auth state and gitignored.
- `cursor/` — Cursor **editor** (GUI) settings (`settings.json`, `keybindings.json`), symlinked from `~/Library/Application Support/Cursor/User/`
- `cursor-agent/` — Cursor **agent CLI** config (distinct from the GUI): `mcp.json` and `statusline.sh` symlinked into `~/.cursor/`; `cli-config.json` is a sanitized copy (auth stripped, not symlinked — Cursor rewrites secrets into the live file). See `cursor-agent/README.md` for restore steps. superpowers installs via `/add-plugin superpowers` in a Cursor chat (no CLI equivalent).
- `karabiner/` — Caps Lock → Esc (tap) / Ctrl (hold); Cmd+Tab → Ctrl+Tab in Cursor
- `borders/bordersrc` — JankyBorders window highlight (auto light/dark)
- `nvim/` — LazyVim config (Space leader, Tokyo Night theme, vim-tmux-navigator). Custom options in `lua/config/options.lua`, plugins in `lua/plugins/`
- `install.sh` / `install-common.sh` / `install-work.sh` / `install-personal.sh` — Profile-based bootstrap. `./install.sh work|personal` dispatches to the matching entry script; both source `install-common.sh` (brew, core dirs, Node LTS via nvm, symlinks, launch agents, theme, cleanup, LazyVim bootstrap, verification) then layer profile-specific packages and links, calling `setup_macos_defaults` (Dock autohide + pinned apps, battery percentage, fast key repeat, Finder hidden files/extensions) after their own Brewfile bundle. Idempotent.
- `Brewfile` / `Brewfile.work` / `Brewfile.personal` — Core packages plus per-profile package sets. Work adds Ledidi/dev tooling (cloudflared, watchman, lefthook, opentofu, aws-vpn-client, Chrome, ngrok, Slack); personal adds ansible, hcloud, helm, k3d, opentofu, Brave + Tailscale.
- `switch-theme.sh` — Set macOS appearance + alacritty theme + borders to `light`/`dark` (arg, or local clock: light 07–18). Run on login and hourly by the `com.philip.theme-watcher` launch agent (`launchd/`) — hourly rather than just at the boundaries because launchd fires StartCalendarInterval in a stale timezone after a TZ change; the script exits early when nothing changed
- `GUIDE.md` — Quick-reference for tools, tmux/nvim shortcuts, shell aliases, layout functions
- `AGENTS.md` (repo root) — What Codex and Cursor load for *this* repo: structure, install/verify commands, shell conventions, Conventional Commit rules. It restates facts from this file, so a change here that invalidates one of them has to be mirrored there.

## Key Patterns

**Worktree workflow**: Worktrees are native — they live at `<repo>/.claude/worktrees/<name>` and nowhere else, so Claude Code's `EnterWorktree` can create and enter them directly. New branch → `EnterWorktree` with an **explicit `name`** (a generated name becomes the Docker stack ID); existing branch → `git worktree add .claude/worktrees/<name> <branch>` then `EnterWorktree path:<path>`. Either way, run `setup-stack` afterwards — it is what writes the untracked `CLAUDE.local.md`/`AGENTS.md`, so a worktree that skips it has none of the project rules loaded. It stays an explicit step: 2.1.220 does ship `WorktreeCreate`/`WorktreeRemove` hook events, but they *supply* the worktree for non-git VCS (the hook must echo a path) rather than firing after `git worktree add`, so neither is wired in `claude/settings.json`. The Docker stack is **opt-in** and tiered by what the task needs: nothing for tsc/biome/frontend unit tests, `dev up postgres -d` for the backend suite (vitest's global setup builds `registries-test` itself), full `dev up` for E2E and browser work. `dev up` fills in the port table itself and `dev down` re-syncs rather than deleting the files, so no follow-up `sync-context` is needed. **Teardown waits until the PR is merged** — agents never run `dev down`, `dev nuke`, or `wt-down` on their own initiative, and a green suite is not a reason to stop the stack. Post-merge teardown is `wt-down`, not `ExitWorktree action:remove` (which deletes the branch and orphans the stack). Stack identity keys on the worktree *directory name*, not the branch, so switching branches inside a worktree keeps its stack and ports.

**Planning and review**: plans come from the work-only `writing-plans` skill (on a personal machine, the plugin's `mattpocock-skills:wayfinder`/`mattpocock-skills:to-tickets` fill that role); local working diffs from the built-in `/code-review`. GitHub PRs go through the work-only `review-pr` skill, which posts inline comments. It carries the test, backend-integration-test, security/authorization, event-sourcing, code-style, frontend and logging rules inline; the architecture and broader backend/style corpus it does *not* repeat lives in `dev/context/ledidi-monorepo/docs/{architecture,backend,code-style,testing}.md`, which it loads by absolute path along with `dev/feedback/SYNTHESIZED_LEARNINGS.md`. `codex/skills/code-review/references/` keeps its own adapted copies of the three retired `ledidi-*` reviewer agents.

**Notification hook**: `dev/claude-notify.sh` handles Claude Code's Stop + Notification events (macOS notifications via `terminal-notifier`), wired via the `hooks` block in `claude/settings.json`. The zsh `notify()` helper sends macOS desktop notifications and prefers `alerter`, falling back to `terminal-notifier` (in the Brewfile — `alerter` is no longer distributed via Homebrew) and then `osascript`.

**Script access**: Dev scripts are invoked via symlinks in `~/bin/` (e.g., `dev`, `tunnel`) and have zsh tab completions defined in `.zshrc`.

**Multi-agent parity**: Claude Code, Codex, and Cursor agent CLI are kept roughly in sync. All three share the `datadog` MCP server (via `dev/mcp-datadog.sh`). Browser control has diverged on purpose: Claude uses the built-in **Claude in Chrome** integration (native messaging host → Claude browser extension → the real, logged-in browser; toggled by the machine-local `claudeInChromeDefaultEnabled` key in `~/.claude.json`, set via `/chrome`), so it no longer runs `chrome-devtools-mcp`. Codex and Cursor keep `chrome-devtools-mcp` because they have no equivalent. Plugins are installed through each tool's own plugin manager (Claude: `enabledPlugins` in `settings.json`; Codex: `codex plugin add` → `[plugins.*]` in `config.toml`; Cursor: `/add-plugin` in-chat). The plugin payloads live in each tool's cache and are NOT version-controlled — only the enablement/config is. superpowers has diverged on purpose too: dropped from Claude's `enabledPlugins` in favour of the four recalibrated copies in `claude/skills.work/`, but left **enabled** on Codex (`[plugins."superpowers@openai-curated"]`), where gpt-5.5 does better with the more prescriptive originals. Custom skills are barely shared at all: Claude has nine, all work-only in `claude/skills.work/`; Codex two (`code-review`, `explain-diff-html`); Cursor **none** — `cursor-agent/` has no skills dir and no install script links one. `explain-diff-html` is the only skill two tools share.

**Work agent config**: The base `claude/settings.json`, `codex/config.toml`, and `cursor-agent/mcp.json` hold only shared content. Work-only bits (Datadog MCP, Claude's `permissions.defaultMode: "bypassPermissions"`, Codex `~/work` project-trusts) live in `*.work.*` overlay files and are merged into real (non-symlink) live files on work machines by `dev/sync-agent-configs.sh` (run by `install-work.sh`; re-run after editing a base/overlay on a work machine). On personal machines the base files stay symlinked. Same idea for SSH: `ssh/config` is the personal base (github.com → `~/.ssh/github`) linked by `install-common.sh`; `ssh/config.work` (github.com → `~/.ssh/github_work`, plus bitbucket) replaces the symlink in `install-work.sh`. Claude skills and agents follow the same split, but via per-entry symlinks rather than an overlay merge: `link_claude_dir` in `install-common.sh` populates `~/.claude/skills` and `~/.claude/agents` from `claude/skills/` and `claude/agents/`, and `install-work.sh` re-runs it with the matching `.work` dirs added. It prunes its own previous links first, so a personal reinstall on a former work machine drops the work skills and agents while leaving any machine-local ones alone; it only ever prunes links pointing into `$DOTFILES/claude`, so machine-local entries stay put. Work shell functions (`wt-down`/`dev`/`prisma`/`sync-context`) live in `zsh/.zshrc.work`, sourced by `.zshrc` only when `~/work` exists.

## When Editing These Configs

- Shell functions/aliases go in `zsh/.zshrc`. Secrets load from `zsh/.zsh_secrets` (gitignored).
- Claude skills go in `claude/skills.work/` (work only) or `claude/skills/` (both profiles — currently empty on purpose, so putting one there is a deliberate choice to load it on personal machines too); agents likewise in `claude/agents.work/` or `claude/agents/`. Settings in `claude/settings.json`. After adding or removing a skill or agent, re-run the installer for the profile — `~/.claude/skills` and `~/.claude/agents` are real directories of per-entry symlinks, not links to the repo.
- Dev scripts are all Bash — `#!/bin/bash` or `#!/usr/bin/env bash`; none use Zsh. Scripts must be executable.
- The `.gitignore` excludes: cagent, configstore, kanata, neofetch, rstudio, raycast, AWSVPNClient, tmp, node_modules, .zsh_secrets, .zcompdump, and `.env` / `.env.*` with `!.env*.example` — so env values go in a `.env.local` and only the `.example` is tracked. This remote is public.

## Shorthand Phrases

- **"update the context"** — Update `CLAUDE.local.md` and `AGENTS.md` under `dev/context/ledidi-monorepo/` (relative to this repo root), plus any files they reference.
